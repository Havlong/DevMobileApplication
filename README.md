# Приложение-пример для курса «Разработка Мобильных приложений» «SignGate: Шлюз ЭДО»

Для демонстрации архитектурных подходов и компонентов в методических указаниях используется
модельное приложение **«SignGate»**. Оно имитирует работу клиентского терминала для локального
подписания электронных документов (ЭД) и последующего взаимодействия со службами шлюза ЭДО
(сервисами валидации DVCS).

## 1. Архитектурные модули и структура экранов

Приложение разделено на четыре функциональных раздела, которые последовательно развиваются от
верстки (ЛР-2) до интеграции локальной БД и сетевого взаимодействия (ЛР-5/6):

* **Мои документы** Перечень электронных документов (ЭД), подписанных локально на устройстве
  текущим пользователем.
* **Полученные документы** Перечень ЭД, полученных от других пользователей (как через шлюз, так и
  через альтернативные каналы связи). К ним может быть прикреплен сертификат проверки, либо они
  могут иметь статус еще не отправленных на проверку.
* **Панель мониторинга** Экран контроля состояния шлюзов валидации данных (с ролевым
  разделением прав: Пользователь / Администратор шлюза).
* **Настройки и Профиль** Локальное управление личными ключами/сертификатами подписи, импорт
  сертификатов шлюза для доверия ему и выбор локального стандарта подписи.

## 2. Матрица состояний и статусов данных

Поскольку полученные документы могут быть еще не проверены шлюзом, матрицы состояний для разделов
«Мои документы» и «Полученные документы» полностью идентичны. Для реализации реактивного слоя и
локального хранения вводится жесткое перечисление (`enum`) состояний объектов:

* **Статусы проверки документов шлюзом:** `NOT_SENT` (Не отправлен на проверку в шлюз ЭДО),
  `VALID` (Положительный сертификат проверки ЭД), `INVALID` (Отрицательный сертификат),
  `GATEWAY_FAILURE` (Технический сбой при проверке документа шлюзом), `CA_VERIFICATION_ERROR`
  (Ошибка при проверке сертификата самого шлюза ЭДО).
* **Контуры инфраструктуры шлюза:** Разделение на **Внутренний сегмент** (контур взаимодействия
  пользователей со шлюзом) и **Внешний сегмент** (контур взаимодействия шлюзов между собой для
  кросс-валидации).

## 3. Ролевая модель и топология дашборда мониторинга

* **Обычный пользователь:** Видит агрегированное, отказоустойчивое состояние «здоровья» сервисов
  Удостоверяющего Центра (УЦ) в разделении на внутренний и внешний сегменты без детальной
  инфраструктурной топологии.
* **Администратор шлюза:** Имеет расширенный доступ, видит состояние конкретных балансируемых
  физических узлов шлюза, доступность сервисов УЦ, а также детальный статус подключенных на стороне
  шлюза криптографических средств (СКЗИ внутреннего и внешнего сегментов: ГОСТ CSP, RSA CSP,
  аппаратные серверные HSM-модули).
